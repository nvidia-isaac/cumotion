class cumotion.RobotDescriptionBuilder#

Interface to build a RobotDescription programmatically.

This interface provides an alternative to loading a RobotDescription from URDF/XRDF files (see load_robot_from_file()).

A builder is initialized with a root frame by create_robot_description_builder(). The robot is then specified by adding frames, the joints that connect them, the c-space coordinates that control those joints, and any collision geometry. A RobotDescription is produced by build().

Each add_*() method validates its input and reports an invalid specification by logging a nonfatal error and returning False, leaving the state of the builder unchanged. This means a failed addition can be corrected and retried, and that a RobotDescription is only ever built from additions that have each been validated.

Frames, joints and c-space coordinates occupy independent namespaces, so a joint and the c-space coordinate that controls it may share a name. Within a namespace, each name must be unique: a frame name is unique among frames, a joint name is unique among joints of ALL types, and a c-space coord name is unique across standard AND auxiliary c-space coordinates. Every name must be non-empty.

A revolute or prismatic joint need not be controlled by a c-space coordinate (standard or auxiliary). Such a joint is not driven by the resulting RobotDescription, and is held at a position of zero clipped to its position limits. Controlling a joint by a c-space coordinate enables overriding its default position.

add_aux_cspace_coord(
self: cumotion.cumotion.RobotDescriptionBuilder,
name: str,
joint_names: collections.abc.Sequence[str],
default_position: SupportsFloat | None = None,
) → bool#

Add an auxiliary c-space coordinate named name to the robot description.

An auxiliary c-space coordinate controls joints that are excluded from the c-space used for motion generation (e.g., a gripper may be controlled by an auxiliary c-space coordinate). Such joints are held at a fixed position.

Unlike a standard c-space coordinate (i.e., a c-space coordinate added via add_cspace_coord()), an auxiliary c-space coord requires no velocity, acceleration, or jerk limits. Any velocity limits set for the joints it controls are ignored.

A valid auxiliary c-space coord specification will add the auxiliary c-space coord and return True. An invalid auxiliary c-space coord specification will log a nonfatal error, make no changes to the state of this builder, and return False.

Each auxiliary c-space coordinate will be assigned an index according to the order in which it is added to the robot description (i.e., the first auxiliary c-space coordinate added will have index 0, the second will have index 1, etc.).

Each auxiliary c-space coord name must be non-empty and unique (as compared to c-space coord names AND auxiliary c-space coord names). Failure to provide a non-empty, unique name constitutes an invalid auxiliary c-space coord specification.

Each auxiliary c-space coord will control one or more joints indicated by joint_names. Any of the below conditions constitute an invalid auxiliary c-space coord specification:

  1. A joint name is included in joint_names for a joint that has not yet been added to the robot description.

  2. A joint name is included more than once in joint_names.

  3. A joint is included in joint_names that is already controlled by another c-space coordinate OR auxiliary c-space coordinate.

  4. One of the names in joint_names corresponds to a fixed joint (i.e., a joint that, by definition, cannot be controlled).

  5. No joint names are provided in joint_names. Each auxiliary c-space coord must control at least one joint.

  6. The position limits of the joints in joint_names do not overlap. Joints with no position limits are permitted, but any limits that are present must intersect to form a valid (non-zero) range.

The position limits of an auxiliary c-space coord are the intersection of the position limits of the joints it controls that have them, expressed in c-space (i.e., accounting for the joint_map of each controlled joint). An auxiliary c-space coord whose controlled joints all lack position limits is unconstrained.

The (optional) default_position is the c-space position at which the controlled joints are held. If no default_position is specified, the default position is zero clipped to the position limits of the auxiliary c-space coord. It is an invalid auxiliary c-space coord specification if a default_position violates those position limits.

add_collision_spheres(
self: cumotion.cumotion.RobotDescriptionBuilder,
frame_name: str,
collision_spheres: collections.abc.Sequence[cumotion.cumotion.RobotDescriptionBuilder.CollisionSphere],
) → bool#

Attach collision_spheres to the frame named frame_name.

The collision_spheres are specified with centers in the local coordinates of frame_name, and are appended to any spheres previously attached to that frame.

A valid collision sphere specification will attach the spheres and return True. An invalid collision sphere specification will log a nonfatal error, make no changes to the state of this builder, and return False. Any of the below conditions constitute an invalid collision sphere specification:

  1. The frame_name has NOT already been added to the robot description,

  2. A sphere in collision_spheres has a non-positive radius,

  3. A sphere in collision_spheres is enabled for neither world-collision nor self-collision, OR

  4. A sphere in collision_spheres has a non-positive effective world- or self-collision radius (i.e., a buffer distance that is not greater than the negated radius).

NOTE: The spheres are attached only if every sphere in collision_spheres is valid.

An empty collision_spheres makes no change to this builder and returns True.

add_cspace_coord(
self: cumotion.cumotion.RobotDescriptionBuilder,
name: str,
joint_names: collections.abc.Sequence[str],
acceleration_limit: SupportsFloat,
jerk_limit: SupportsFloat,
default_position: SupportsFloat | None = None,
) → bool#

Add a c-space coordinate named name to the robot description.

These “standard” c-space coordinates are used for motion generation and generally referred to simply as “c-space coordinates”. The full configuration space of the robot also includes “auxiliary” c-space coordinates. See add_aux_cspace_coord() for details.

A valid c-space coord specification will add the c-space coord and return True. An invalid c-space coord specification will log a nonfatal error, make no changes to the state of this builder, and return False.

Each c-space coordinate will be assigned an index according to the order in which it is added to the robot description (i.e., the first c-space coordinate added will have index 0, the second will have index 1, etc.). This index corresponds to the name order reported by RobotDescription.cspace_coord_name().

Each c-space coord name must be non-empty and unique (as compared to c-space coord names AND auxiliary c-space coord names). Failure to provide a non-empty, unique name constitutes an invalid c-space coord specification.

Each c-space coord will control one or more joints indicated by joint_names. Any of the below conditions constitute an invalid c-space coord specification:

  1. A joint name is included in joint_names for a joint that has not yet been added to the robot description.

  2. A joint name is included more than once in joint_names.

  3. A joint is included in joint_names that is already controlled by another c-space coordinate OR auxiliary c-space coordinate.

  4. One of the names in joint_names corresponds to a fixed joint (i.e., a joint that, by definition, cannot be controlled).

  5. No joint names are provided in joint_names. Each c-space coord must control at least one joint.

  6. No joint in joint_names has position limits. At least one controlled joint must have position limits specified.

  7. No joint in joint_names has a velocity limit. At least one controlled joint must have a velocity limit specified.

  8. The position limits of the joints in joint_names do not intersect to form a valid (non-zero) range.

A c-space position is dimensionless, and is converted to the position of each controlled joint by the joint_map of that joint. A single c-space coord may therefore control a mix of prismatic and revolute joints.

An acceleration_limit and a jerk_limit are required for every c-space coord, and are expressed in c-space units per second squared and per second cubed, respectively. It is an invalid c-space coord specification if either limit is not positive.

The position limits of a c-space coord are the intersection of the position limits of the joints it controls, expressed in c-space (i.e., accounting for the joint_map of each controlled joint).

The (optional) default_position is a c-space position reported by RobotDescription.default_cspace_configuration(). If no default_position is specified, the default position is zero clipped to the position limits of the c-space coord. It is an invalid c-space coord specification if a default_position violates those position limits.

Add a fixed joint named name to the robot description.

A valid joint specification will add the joint and return True. An invalid joint specification will log a nonfatal error, make no changes to the state of this builder, and return False.

Each joint name must be non-empty and unique (as compared to existing joint names of ALL joint types). Failure to provide a non-empty, unique name constitutes an invalid joint specification.

The joint connects frames with names parent_frame_name and child_frame_name. Any of the below conditions constitute an invalid joint specification:

  1. Frames with these names have NOT already been added to the robot description. The joint must connect existing frames.

  2. The frame corresponding to child_frame_name has been previously added as the child frame of another joint. This is because each frame can only be directly controlled by a single joint.   4. The parent_frame_name and child_frame_name are the same.

add_self_collision_mask(
self: cumotion.cumotion.RobotDescriptionBuilder,
frame_name: str,
masked_frame_names: collections.abc.Sequence[str],
) → bool#

Mask self-collision between the frame named frame_name and each frame in masked_frame_names.

Intersection between the self-collision spheres of a masked pair of frames does NOT constitute a self-collision. This is typically used for pairs of frames that are:

  • always in contact (e.g., adjacent links), or

  • never in contact (i.e., frames for which collision is impossible).

NOTE: Masking is symmetric, so a pair only needs to be masked in one direction.

Masked frame names are appended to any previously specified for frame_name, and duplicates are ignored. The frame_name itself is also ignored if it is included in masked_frame_names, since self-collision is never evaluated between the spheres of a single frame.

It is an invalid self-collision mask specification if frame_name, or any name in masked_frame_names, has not already been added to the robot description, in which case a nonfatal error is logged, no changes are made to the state of this builder, and False is returned.

A masked_frame_names that names no frame other than frame_name, including an empty masked_frame_names, makes no change to this builder and returns True.

NOTE: A mask is only meaningful between frames that have self-collision spheres. A mask

involving a frame with no self-collision spheres is discarded (with a warning) by build().

build(
self: cumotion.cumotion.RobotDescriptionBuilder,
) → cumotion.cumotion.RobotDescription#

Create a RobotDescription from the specified frames, joints, c-space coordinates, and collision geometry.

Any frames not connected to the root frame will be discarded from the returned RobotDescription, as will collision spheres attached to those frames and any self-collision masks involving those frames.

Each returned RobotDescription is fully independent from other built robot descriptions. Likewise, any additions to the builder after calling build() will not be reflected in previously built robot descriptions.

A nonfatal error will be logged if a tool frame is not connected to the root frame, in which case it is omitted from RobotDescription.tool_frame_names().

A warning will be logged for each frame that is not connected to the root frame, and for each joint that drives such a frame, identifying what has been discarded.

A warning will also be logged, and the affected geometry discarded, if:

  1. A self-collision mask involves a frame with no self-collision spheres, OR

  2. A frame with attached collision spheres is not connected to the root frame.

A fatal error will be logged if a c-space (standard or auxiliary) coordinate would:

  1. Control no joints because every joint it controls is discarded with a frame that is not connected to the root frame, OR

  2. Have insufficient position and/or velocity limit specification among the joints that remain after such discarding.

class SdfInspectionTolerances#

Tolerances used when inspecting an SDF.

Accumulation of numerical error from type-casting is handled independently of the tolerances in SdfInspectionTolerances. It is expected that any SDF computed from an analytically correct distance function will pass inspect_sdf() with the default tolerances of 0.0.

Inspection tolerances are specified in single-precision (float) because only single- and half-precision data for device-resident SDFs are supported.

property voxel_matches_neighbor_tolerance#

Numerical tolerance on checking whether an SDF voxel value is equal to its neighbor.

The effective tolerance used is the combination of this tolerance and an internally computed numerical_tolerance. numerical_tolerance is a derived upper bound on accumulated error under the assumption that SDF data was computed analytically with infinite precision, then cast to the data type specified by the device_precision of the associated Obstacle.Grid.

A voxel is said to be equal to its neighbor if: abs(voxel_value - neighbor_value) <= voxel_matches_neighbor_tolerance + numerical_tolerance.

This tolerance must be non-negative.

property voxel_too_far_from_neighbor_tolerance#

Numerical tolerance on checking whether an SDF voxel value is too far from a neighboring voxel.

The effective tolerance used is the combination of this tolerance and an internally computed numerical_tolerance. numerical_tolerance is a derived upper bound on accumulated error under the assumption that SDF data was computed analytically with infinite precision, then cast to the data type specified by the device_precision of the associated Obstacle.Grid.

A voxel is said to be too far from its neighbor if: abs(voxel_value - neighbor_value) > voxel_size + voxel_too_far_from_neighbor_tolerance + numerical_tolerance, where voxel_size is the voxel_size of the associated Obstacle.Grid.

This tolerance must be non-negative.

class CSpaceLimitBiasing#

The error function for BFGS descent optionally includes a cost-term for avoiding c-space coordinate values near position limits.

If set to ENABLE, this cost term will always be turned on. If set to DISABLE, this cost term will always be turned off. cumotion.solve_ik(
kinematics: cumotion.cumotion.Kinematics,
target_pose: cumotion.cumotion.Pose3,
target_frame: str,
config: cumotion.cumotion.IkConfig,
) → cumotion.cumotion.IkResults#

Attempt to solve inverse kinematics.

A target_pose is provided for the task-space frame named by target_frame and the solver attempts to find a corresponding set of c-space coordinates. A valid c-space configuration must not exceed position limits set in the kinematic structure and must reach the target pose within the tolerances specified by config.

If the target_frame is selected such that some of the c-space coordinates do not affect the pose of the target frame, these “downstream” coordinates will be ignored by the IK solver. For the case where the successful descent was started from a seed provided in config.cspace_seeds, the “downstream” coordinates will not be altered from the provided seed. For the case where a random seed is used, the “downstream” coordinates will be returned with values between their respective c-space position limits. This behavior is intended to support cases such as branched kinematic structures (i.e., to solve for palm pose of a robotic system with an arm and multiple fingers) or a redundant serial linkage for which it is desired to set a pose of a frame not rigidly fixed to the end effector.

A fatal error will be logged if target_frame is not a valid frame name.

This implementation of cyclic coordinate descent (CCD) is based on “A Combined Optimization Method for Solving the Inverse Kinematics Problem of Mechanical Manipulators” (1991) by Wang et al. Ref: http://web.cse.ohio-state.edu/~parent.1/classes/788/Sp06/ReferenceMaterial/IK/WC91.pdf

As described by Wang et al., this “combined” method uses cyclic coordinate descent (CCD) as a quick method to find a feasible c-space position that is in the neighborhood of an exact solution to the inverse kinematics problem. These nearby c-space positions are then used to “warm start” the Broyden-Fletcher-Goldfarb-Shanno (BFGS) algorithm. Given a point sufficiently near an exact solution, the BFGS algorithm is able to leverage an estimate of curvature to rapidly converge to a very accurate approximation of the exact solution.

Concise explanations of the CCD algorithm with interactive demonstrations are available at: [1] https://zalo.github.io/blog/inverse-kinematics/ [2] http://rodolphe-vaillant.fr/?e=114

The following parameters can be set for TrajectoryOptimizer:

enable_self_collision [bool]

  • Enable or disable self-collision avoidance between robot spheres during optimization.

  • When True, both inverse kinematics (IK) and trajectory optimization will include collision costs to prevent robot spheres from colliding with each other.

  • When False, self-collision costs are disabled, which may improve solve time but allows self-intersecting trajectories.

  • Default value is True (self-collision avoidance enabled).

  • DEPRECATED: A deprecation warning is logged when enable_self_collision is set via set_param() or when present in a configuration file. The value is still applied in this release. This parameter will be removed in a future release.

enable_world_collision [bool]

  • Enable or disable collision avoidance with world obstacles during optimization.

  • When True, both IK and trajectory optimization will include collision costs to avoid obstacles in the environment.

  • When False, world collision costs are disabled, which may improve performance but allows trajectories that intersect with obstacles.

  • Default value is True (world collision avoidance enabled).

  • DEPRECATED: A deprecation warning is logged when enable_world_collision is set via set_param() or when present in a configuration file. The value is still applied in this release. This parameter will be removed in a future release.

task_space_terminal_position_tolerance [double]

  • Maximum allowable violation of the user-specified constraint on the position of the tool frame.

  • Used both for IK and trajectory optimization problems. It determines when a solution is considered to have satisfied position targets. Smaller values require more precise solutions but may be harder to achieve.

  • Units are in meters.

  • A default value of 1e-3 (1mm) is recommended for most use-cases.

  • Must be positive.

task_space_terminal_orientation_tolerance [double]

  • Maximum allowable violation of the user-specified constraint on the orientation of the tool frame.

  • Used both for IK and trajectory optimization problems. It determines when a solution is considered to have satisfied orientation targets. Smaller values require more precise solutions but may be harder to achieve.

  • Units are in radians.

  • A default value of 5e-3 (approximately 0.29 degrees) is recommended for most use-cases.

  • Must be positive.

ik/num_seeds [int]

  • Number of seeds used to solve the inverse kinematics (IK) problem.

  • The trajectory optimizer generates multiple pseudo-random c-space configurations and optimizes them to find diverse collision-free configurations for the desired tool pose. Higher values increase the likelihood of finding valid solutions but increase computational cost.

  • A default value of 32 is recommended for most use-cases.

  • Must be positive.

ik/max_reattempts [int]

  • Maximum number of times to restart the IK problem with different random seeds, in case of failure, before giving up.

  • Higher values increase the likelihood of finding valid IK solutions but increase memory usage and the maximum possible time to find a solution. A value of 0 means no retries (i.e. only perform the initial attempt).

  • A default value of 10 is recommended for most use-cases.

  • Must be in the range [0, 50].

  • A default value of 1.0 provides balanced behavior for most use-cases.

Create a TranslationConstraint such that a translation_target is specified at termination AND a linear translation constraint is active along the path.

The linear path constraint is defined by the line segment between translation_target and the origin of the tool frame at the initial c-space position. This path constraint is satisfied if the origin of the tool frame is on this line segment between the initial and final tool positions at all points in the trajectory. It is considered a constraint violation if the origin of the tool frame “overshoots” either the initial or final positions.

If the distance between the initial and final tool frames are nearly the same, the path constraint becomes a constraint on the distance from the initial and final positions in any direction.

The optional parameters path_deviation_limit and terminal_deviation_limit can be used to allow deviations from the specified line along the path and at the end of the path, respectively.

If both limits are input, the path_deviation_limit must be greater than or equal to (i.e., no more restrictive than) the terminal_deviation_limit.

If neither is input, then both deviation limits are assumed to be zero, indicating that translation should always be exactly coincident with the specified line.

It is valid to input a path_deviation_limit without a terminal_deviation_limit (implicitly setting the latter to zero) but not to input a terminal_deviation_limit without a path_deviation_limit. This ensures that the terminal constraint is more restrictive than the corresponding path constraint.

A fatal error will be logged if:

  1. path_deviation_limit is negative,

  2. terminal_deviation_limit is negative,

  3. both path_deviation_limit and terminal_deviation_limit are defined, but path_deviation_limit < terminal_deviation_limit, OR

  4. terminal_deviation_limit is defined without defining a path_deviation_limit.

NOTE: The translation_target is specified in world frame coordinates (i.e., relative to the base of the robot).

class cumotion.TaskSpacePathSpec#

The TaskSpacePathSpec is used to procedurally specify a TaskSpacePath from a series of continuous task-space segments.

Each segment can have position that is:

[1] constant, [2] linearly interpolated, [3] or defined by a circular arc.

For the case where position follows an arc, the arc can be defined either by a series of three points, or by two endpoints and a constraint that the arc be tangent to the previous segment.

Each segment may have orientation that is:

[1] constant (w.r.t. the fixed global frame), [2] smoothly blended via spherical linear interpolation (i.e., “slerp”), or [3] constant w.r.t. the tangent direction of the position path (i.e., “tangent orientation”).

The “tangent orientation” specification is only relevant for path segments for which position is defined by an arc (since for linear position paths, the “tangent orientation” specification would reduce to a constant orientation w.r.t. the fixed global frame).

Load a TaskSpacePathSpec from file with absolute path task_space_path_spec_file.

The task_space_path_spec_file is expected to correspond to a YAML file specifying a task-space path. This path specification must include:

  1. an initial task-space pose, and

  2. a series of path segments emanating from this initial pose.

The initial pose uses the key “initial pose” and is expected to have the following format:

initial pose:
  position: [#, #, #]
  orientation: {w: #, xyz: [#, #, #]}

where each “#” represents a floating point value. Position must be a 3d-vector and orientation is represented by a quaternion.

NOTE: Standard YAML formatting is allowed, wherein:

  • mapped keys can be included in any order (e.g., “position” and “orientation” can be included in either order),

  • mapped keys can be included on a single comma-separated line with curly braces, or expanded to multiple lines. E.g., “orientation” can be formatted as:

    orientation: {w: #, xyz: [#, #, #]}

    or equivalently as:

    orientation:
  w: #
  xyz: [#, #, #]

  • sequences can be included in a single comma-separated line with square brackets, or expanded into multiple lines with preceding dashes. E.g., “position” can be formatted as:

    position: [#, #, #]

    or equivalently as:

    position:
  - #
  - #
  - #

The path segments are specified as a sequence under the key “path specs”. Each path specification must specify both a “position mode” and an “orientation mode”.

The “position mode” must be:

  • “linear”,

  • “constant”,

  • “three_point_arc”, or

  • “tangent_arc”.

The “orientation mode” must be:

  • “slerp”,

  • “constant”, or

  • “tangent”.

WARNING: Not all combinations of “position mode” and “orientation mode” are compatible. Specifically, a “linear” position mode is NOT compatible with a “tangent” orientation mode. A “constant” position mode is ONLY compatible with a “slerp” orientation mode. The two arc position modes (“three_point_arc” and “tangent_arc”) are compatible with all orientation modes.

The composite_path_spec_file is expected to correspond to a YAML file specifying a path composed of task-space and/or c-space segments. This path specification must include:

  1. an initial c-space position, and

  2. a series of task-space and/or c-space path specifications following this initial c-space position.

The initial c-space position uses the key “initial c-space position” and is expected to have the following format:

initial c-space position: [#, #, ... , #]

initial c-space position: [#, #, ... , #]

      initial c-space position: [#, #, ... , #]
      waypoints:

        - ...
        - [#, #, ... , #]

Create default set of configuration parameters for converting a TaskSpacePathSpec into a series of c-space configurations.

Default parameters are expected to work well for converting most task space paths to c-space paths.

If a tighter tolerance for adherence to the task space path is desired, then the min_position_deviation and/or max_position_deviation can be decreased (at the expense of more computational cost and more c-space waypoints which will likely lead to trajectories with longer time-spans). Conversely, tolerances can be loosened for faster path conversion and/or (likely) faster trajectories.

Beyond (optionally) adjusting position deviations, it is unlikely that other parameters will need to be modified from the provided default values.

property alpha#

“alpha” is used to exponentially scale the s step size “delta” to speed convergence when the s step size is being successively increased or successively decreased. When an increase is followed by a decrease, or vice versa, “alpha” is used to decrease the s step size “delta” to reduce overshoot. The default value is generally recommended. alpha must be greater than 1. Default value is 1.4.

property initial_s_step_size#

Initial step size in the domain value s used to sample poses from the task space path to be converted to c-space waypoints. The s step size will be adaptively updated throughout the path conversion and the default value for initialization is generally recommended. initial_s_step_size must be positive. Default value is 0.05.

property initial_s_step_size_delta#

Initial step size “delta” that is used to adaptively adjust the s step size; s is the domain value s used to sample poses from the task space path to be converted to c-space waypoints. The s step size “delta” will be adaptively updated throughout the path conversion and the default value for initialization is generally recommended. initial_s_step_size_delta must be positive. Default value is 0.005.

property max_iterations#

Maximum number of iterations to search for each c-space waypoint. If max_iterations is reached for any c-space waypoint, then path conversion will fail. max_iterations must be positive. Default value is 50.

property max_position_deviation#

For each c-space waypoint that is generated, the position deviation between the desired task space path and a task space mapping of a straight-line interpolation in c-space is approximated. The maximum position deviation places an upper bound of deviation allowed to add a c-space waypoint. max_position_deviation must be positive and greater than min_position_deviation. Default value is 0.003.

property min_position_deviation#

For each c-space waypoint that is generated, the position deviation between the desired task space path and a task space mapping of a straight-line interpolation in c-space is approximated. The minimum position deviation places a lower bound of deviation required to add a c-space waypoint. While it is somewhat unintuitive that the deviation could be too small, this minimum deviation is used to control the minimum spacing between c-space configurations along the task space path domain. A (relatively) sparse series of c-space waypoints is desirable for trajectory generation; if the minimum deviation is arbitrarily small then the c-space points will be (in general) too close together to generate a time-optimal trajectory. Generation of excessive c-space waypoints will also be computationally expensive and is, in general, best avoided. min_position_deviation must be positive and less than max_position_deviation. Default value is 0.001.

property min_s_step_size#

Minimum allowable interval in domain value s that can separate poses from the task space path to be converted to c-space waypoints. The minimum s step size serves to limit the number of c-space configurations that can be returned in the converted path. Specifically, the upper bound for the number of returned c-space configurations is (“span of the task space path domain” / min_s_step_size) + 1. min_s_step_size must be positive. Default value is 1e-5.

property min_s_step_size_delta#

Minimum allowable s step size “delta” used to adaptively update the s step size. The min_s_step_size_delta serves to limit wasted iterations when (minimal) progress is being made towards path conversion. If min_s_step_size_delta is reached during the search for any c-space waypoint, then path conversion will fail. The default value is generally recommended. min_s_step_size_delta must be positive. Default value is 1e-5.

class cumotion.CSpaceTrajectoryGenerator#

Configure a trajectory generator that can compute smooth* trajectories. A trajectory generation problem is specified by:

  1. Position waypoints, and

  2. Limits on some combination of position, velocity, acceleration and jerk.

Times for the waypoints are not specified. It is assumed that a time-optimal trajectory that respects the constraints (with the definition of time-optimality being implementation-specific) will be generated.

  • The definition of “smooth” is implementation-specific. Currently, CSpaceTrajectoryGenerator uses a single implementation that interpolates through waypoints using a series of cubic splines. For this implementation, “smooth” is defined as smooth velocity, continuous acceleration, and bounded jerk.

class InterpolationMode#

Interpolation modes used by generate_time_stamped_trajectory().

Members:

LINEAR : Linear interpolation between c-space positions. The resulting trajectory will have continuous (but not smooth) position and discontinuous segments of constant velocity. Acceleration and jerk will be returned as zero (including at velocity discontinuities where values are technically undefined).

CUBIC_SPLINE : Piecewise solution with a cubic spline between adjacent c-space positions. The resulting trajectory will have smooth position and velocity, continuous (but not smooth) acceleration, and bounded (but discontinuous) jerk.

Set the value of the solver parameter.

Currently, CSpaceTrajectoryGenerator uses a single solver implementation based on computing a series of cubic splines. The following parameters can be set for this piecewise cubic spline solver:

max_segment_iterations [int]

  • The first step towards finding a time-optimal trajectory using a series of cubic splines is to iteratively compute an optimal span for each spline segment.

  • Setting a relatively high max_segment_iterations will, in general, result in shorter trajectory time spans, but will tend to take longer to converge.

  • This step can be skipped completely by setting max_segment_iterations to zero.

  • max_segment_iterations must be non-negative. Additionally at least one of max_segment_iterations and max_aggregate_iterations must be non-zero.

  • Default value is 5.

max_aggregate_iterations [int]

  • The second step towards finding a time-optimal trajectory using a series of cubic splines is to iteratively compute an optimal span for the entire trajectory.

  • Relying more heavily on this second step (i.e., setting max_segment_iterations to a relatively low value) will, in general, require less iterations (and thus less time) to converge, but the generated trajectories will tend to have longer time spans.

  • This step can be skipped completely by setting max_aggregate_iterations to zero.

  • max_aggregate_iterations must be non-negative. Additionally at least one of max_segment_iterations and max_aggregate_iterations must be non-zero.

  • Default value is 50.

convergence_dt [float]

  • The search for optimal time values will terminate if the maximum change to any time value during a given iteration is less than the convergence_dt.

  • convergence_dt must be positive.

  • Default value is 0.001.

max_dilation_iterations [int]

  • After the segment-wise and/or aggregate time-optimal search has converged or reached maximum iterations, the resulting set of splines will be tested to see if any derivative limits are exceeded.

  • If any derivative limits are exceeded, the splines will be iteratively scaled in time to reduce the maximum achieved derivative. This process will repeat until no derivative limits are exceeded (success) or max_dilation_iterations are reached (failure).

  • max_dilation_iterations must be non-negative.

  • Default value is 100.

dilation_dt [float]

  • For the iterative dilation step described in max_dilation_iterations documentation, the dilation_dt is the “epsilon” value added to the span of the trajectory that exceeds derivative limits.

  • dilation_dt must be positive.

  • Default value is 0.001.

min_time_span [float]

  • Specify the minimum allowable time span between adjacent waypoints/endpoints.

  • min_time_span must be positive.

  • Default value is 0.01.

time_split_method [str]

  • Specify the TimeSplitMethod for the initial distribution of time values that will be used to iteratively search for time-optimal values.

  • Valid settings are uniform, chord_length and centripetal.

  • Default value is centripetal.

The following parameters can be set for PathPlanner:

  • Used to initialize random sampling.

  • Any value is accepted.

  • Default: 12345.

max_num_segments_per_forest [int]

  • Maximum number of segments in a single planner forest. Internally, this parameter value may be inflated to ensure that at least one iteration of the planner is always possible.

  • Must be positive.

  • The default value of 20000 is recommended for RTX 5090 GPUs, and alternative tunings for different architectures are provided in the content/nvidia/shared/ directory.

num_validation_checks_per_extension [int]

  • Number of validation checks per extension. Increasing this parameter will result in launching a smaller number of extensions in parallel that are individually longer.

  • In practice, increasing this parameter typically results in fewer iterations to solve, at the cost of longer output paths.

  • The length of each extension is up to step_size * num_validation_checks_per_extension.

  • Must be positive, and large enough that num_validation_checks_per_extension * step_size is at least min_extension_length.

  • The default value of 200 (paired with the default step_size of 0.01) is a good starting point for most use-cases.

  • Step size between validated c-space configurations in the returned path. It is assumed that step_size is sufficiently small such that in a contiguous sequence of valid nodes with the distance between neighbors no larger than step_size, the continuous path connecting the nodes is also valid.

  • The length of each extension is up to step_size * num_validation_checks_per_extension.

  • Must be positive, and large enough that num_validation_checks_per_extension * step_size is at least min_extension_length.

  • The default value of 0.01 is recommended for most use-cases.

num_spheres_per_validation_iteration [int]

  • Number of sphere collision checks per iteration. This value is used to determine the total amount of validation work (in terms of individual robot sphere collision checks) that will be performed in each planner iteration. I.e., robots with more collision spheres have a smaller number of parallel extension validations.

  • Internally, a minimum number of parallel extensions is required for efficient path planning. This minimum creates an effective lower bound on num_spheres_per_validation_iteration; decreasing num_spheres_per_validation_iteration below this lower bound will have no effect.

  • NOTE: This parameter is intended to account for the difference in available resources between different GPU architectures.

  • Must be positive.

  • The default value of 600000 is recommended for RTX 5090 GPUs, and alternative tunings for different architectures are provided in the content/nvidia/shared/ directory.

min_extension_length [double]

  • Minimum length in c-space for an extension to be retained.

  • It is observed in practice that allowing short extensions (on the order of 1 to 10 times step_size) corresponds to an increase in the number of total iterations required to find a solution.

  • Must be positive, and less than or equal to num_validation_checks_per_extension * step_size.

  • The default value of 0.3 is recommended for most use-cases, paired with the default extension length of step_size * num_validation_checks_per_extension = 0.01 * 200 = 2.0.

num_shortcut_iterations [int]

  • Number of shortcutting iterations per path. The number of shortcutting iterations hits diminishing returns based on the difficulty of the environment. I.e., in environments with long multi-segment paths, iterative shortcutting will yield worthwhile incremental improvements for more iterations.

  • As the number of paths to return increases, the shortcutting stage will scale linearly in time, while the time to find the requested number of solutions will scale sublinearly. I.e., when returning upwards of 50 paths, the shortcutting stage will dominate solve time.

  • A value of 0 will disable shortcutting.

  • Must be non-negative.

  • The default value of 10 is recommended for most use-cases.

max_iterations [int]

  • Maximum number of iterations executed by the planner. Planning always stops once this many iterations have been executed, whether or not the requested number of paths have been found.

  • If the planner stops due to this parameter without finding any path, Results will report that path_found() is False and num_solutions() is zero.

  • If the planner stops due to this parameter having found fewer paths than requested, it will re-use the paths that it found in order to return the requested number of paths.

  • Must be positive.

  • The default value of 2000 is recommended for RTX 5090 GPUs, where the per-iteration time for robots with less than 100 collision spheres is typically around 0.5 ms. It has been observed in practice that only planning problems which require navigating tight spaces require more than 10 iterations to solve.

post_initial_solve_maximum_iterations [int]

  • Maximum number of iterations executed after the first solution is found. Once the first valid path is found, planning runs at most this many additional iterations before stopping, unless the requested number of paths are collected sooner.

  • If the planner stops early due to this parameter, it will re-use solutions multiple times with different shortcutting seeds in order to return the requested number of paths.

  • Must be non-negative.

  • The default value of 20 is recommended for most use-cases.

plan_to_cspace_targets(
self: cumotion.cumotion.PathPlanner,
initial_cspace_position: Annotated[numpy.typing.ArrayLike, numpy.float64, '[m, 1]'],
cspace_targets: collections.abc.Sequence[Annotated[numpy.typing.ArrayLike, numpy.float64, '[m, 1]']],
num_paths_to_return: SupportsInt = 1,
generate_interpolated_path: bool = False,
) → cumotion.cumotion.PathPlanner.Results#

Compute a set of collision-free paths from initial_cspace_position to at least one of the targets in cspace_targets and return them in ascending order of path length.

num_paths_to_return is the number of solutions to return. The number of returned paths will always be either num_paths_to_return exactly, or zero if no paths are found. In general, the returned paths will be mutually distinct from each other. There are two exceptions:

  1. The planner finds direct collision-free connections between initial_cspace_position and one or more of the targets in cspace_targets. In this case, only direct connection paths will be returned, duplicating them as needed to fill the return slots.

  2. The planner stops before num_paths_to_return paths are found, for example because max_iterations is reached. In this case, the paths that were found are re-used to fill the remaining return slots. Re-used paths are shortcut with distinct seeds, so they are exact duplicates of each other only when shortcutting is disabled.

If generate_interpolated_path is set to True, Solution.interpolated_path() will be populated for each returned PathPlanner.Solution.

A non-fatal error will be logged and a planning failure (i.e., Results for which path_found() is False) returned, if initial_cspace_position or ALL elements of cspace_targets are invalid c-space positions by:

  1. Violating c-space position limits, OR

  2. Being in world- or self- collision.

Each invalid element of cspace_targets will be removed prior to planning with a warning.

A fatal error will be logged if:

  1. len(cspace_targets) is outside the range [1, 1024], OR

  2. initial_cspace_position or any element of cspace_targets has a size different from the robot description used to create PathPlannerConfig, OR

  3. num_paths_to_return is not positive.

Generate a set of num_spheres that approximate the volume of the specified mesh.

If radius_offset is set to zero, all of the generated spheres will be (approximately) tangent to at least two triangles in the mesh. A positive radius_offset will increase the radii of all spheres by adding radius_offset (e.g., a radius_offset of 0.05 will allow spheres to extend beyond the mesh by up to 0.05).   1. Fewer than two triangles remain after the discards described for create_collision_sphere_generator(),

  2. min_sphere_radius is not less than half the diagonal of the axis-aligned bounding box enclosing the mesh vertices, OR

  3. num_spheres is negative or exceeds the number of sampled spheres (see get_sampled_spheres()).

set_param(
self: cumotion.cumotion.CollisionSphereGenerator,
param_name: str,
value: cumotion.cumotion.CollisionSphereGenerator.ParamValue,
) → bool#

Set the value of the parameter.

If the value has been successfully updated, True is returned. If an invalid value has been specified for a parameter, a verbose warning is logged, False is returned and the parameter value is NOT updated. If param_name is not one of the parameters listed below, a warning is logged and False is returned.

A fatal error is logged if value does not hold the type listed for param_name (e.g., an int for a float parameter).

Default parameters are expected to work well for most meshes commonly used to represent robots (i.e., generally “meter scale”). If the meshes are particularly larger or smaller (or represented in units other than meters), then min_sphere_radius, convergence_radius_tol, surface_offset, min_triangle_area, and num_voxels can be scaled appropriately.

Likewise, the default parameters assume a conventional counter-clockwise winding order for vertex indices. If this is not the case, flip_normals can be set to True.

Finally, increasing num_medial_sphere_samples may increase the quality of the selected spheres (at the expense of more processing time).

The full set of parameters that can be set are:

num_medial_sphere_samples [int]

  • The collision sphere generation begins by sampling medial spheres uniformly from the surface of the provided mesh. The medial axis of a mesh is the set of all points having more than one closest point to the mesh. The medial spheres are spheres centered on the medial axis with radius set to the minimum distance from the mesh. By definition, these medial spheres are tangent to at least two faces of the mesh.

  • These sampled spheres are the set from which the minimal set of spheres to approximate the mesh will be selected. A larger number of samples may result in a better selection of spheres, and more spheres may be valuable if the mesh is particularly complex.

  • num_medial_sphere_samples must be positive.

  • Default value is 500.

flip_normals [bool]

  • The mesh input to the CollisionSphereGenerator is not required to be strictly watertight, but is expected to generally represent a volume. Spheres will be generated by sampling points on the triangular mesh faces and “growing” the spheres inwards to find a sphere that is tangent to both the original triangle and some other triangle on the mesh.

  • It is expected that for any point on any triangular face, a sphere that is tangent to that point on the “inside” (negative normal direction) of the triangle with diameter set to the maximum extent on the mesh will intersect at least one other triangle.

  • The normal is by default computed assuming a counter-clockwise winding direction for vertex indices. If the mesh is input with clockwise winding direction for vertex indices, then flip_normals should be set to True to reverse winding order.

  • Default value is False.

min_sphere_radius [float]

  • When generating medial spheres, any spheres that are found to have radius less than min_sphere_radius will be discarded.

  • NOTE: Discarded spheres still count towards num_medial_sphere_samples. E.g., if generate_spheres() is called with num_medial_sphere_samples = 500, and 20 spheres are discarded for being too small, then the actual number of spheres that will be used to select the final spheres is 480.

  • min_sphere_radius must be positive.

  • Default value is 1e-3.

seed [int]

  • Random seed used for sampling surface points on mesh from which to sample spheres.

  • seed must be positive.

  • Default value is 12345.

max_iterations [int]

  • Maximum number of iterations of binary search used to approximate the radius of each medial sphere.

  • NOTE: If max_iterations is reached, the sphere will be discarded. Discarded spheres still count towards num_medial_sphere_samples. E.g., if generate_spheres() is called with num_medial_sphere_samples = 500, and 20 spheres are discarded for not converging to the medial sphere radius tolerance within the max_iterations, then the actual number of spheres that will be used to select the final spheres is 480.

  • max_iterations must be positive.

  • Default value is 100.

convergence_radius_tol [float]

  • Convergence criteria for binary search used to approximate the radius of each medial sphere. The search will end when the sphere radius is within convergence_radius_tol of the actual medial sphere radius.

  • convergence_radius_tol must be positive.

  • Default value is 1e-3.

surface_offset [float]

  • When points are sampled from the mesh surface to generate medial spheres, they are offset by surface_offset towards the “inside” of the mesh in order to avoid collisions with faces very close to the sampling face. This is to help avoid very small spheres that would be culled due to the min_sphere_radius.

  • surface_offset must be positive.

  • Default value is 1e-4.

min_triangle_area [float]

  • Triangles with area less than or equal to min_triangle_area are discarded when creating the mesh for generating medial spheres. This includes degenerate triangles where surface area approaches zero as well as relatively small triangles that will increase computation cost without being likely to improve the set of sampled spheres.

  • min_triangle_area must be positive.

  • Default value is 1e-8.

num_voxels [int]

  • A voxel grid is used to estimate volume additions from each sphere when selecting spheres from the full sample of medial spheres. The num_voxels provides a trade-off between accurate volume approximation (with larger num_voxels) and faster selection (with smaller num_voxels).

  • num_voxels specifies the number of voxels along the longest dimension of an axis-aligned bounding box (AABB) encompassing the specified mesh. For example, if the AABB has dimensions {20, 50, 30} and num_voxels is set to 100, then each voxel will have side length 50 / 100 = 0.5. Thus, the number of voxels along each axis of the grid will be [40, 100, 60].

  • num_voxels must be positive.

  • Default value is 50.

cumotion.create_collision_sphere_generator(
vertices: collections.abc.Sequence[Annotated[numpy.typing.ArrayLike, numpy.float64, '[3, 1]']],
triangles: collections.abc.Sequence[Annotated[numpy.typing.ArrayLike, numpy.int32, '[3, 1]']],
) → cumotion.cumotion.CollisionSphereGenerator#

Create a CollisionSphereGenerator to generate spheres that approximate the volume of a mesh represented by vertices and triangles.

Each vertex in vertices is a set of (x,y,z) coordinates that can be referenced by one or more triangles in triangles. Each triangle is a set of indices in the vertices list.

Vertex indices for a given triangle are considered valid if:

[a] The index for each vertex is in range [0, len(vertices)), and [b] The same index is NOT included twice.

Triangles with invalid indices will be discarded with verbose warnings.

Additionally, each triangle in triangles is tested to ensure that its area is greater than min_triangle_area (see CollisionSphereGenerator.set_param() documentation for details). Triangles that are too small will be discarded. At least two triangles must remain for CollisionSphereGenerator.generate_spheres() to return any spheres.

By default, the triangle normals will be computed assuming a counter-clockwise winding direction. This convention can be flipped by setting flip_normals (see CollisionSphereGenerator.set_param() documentation for details).

cumotion.generate_collision_spheres(
vertices: collections.abc.Sequence[Annotated[numpy.typing.ArrayLike, numpy.float64, '[3, 1]']],
triangles: collections.abc.Sequence[Annotated[numpy.typing.ArrayLike, numpy.int32, '[3, 1]']],
max_overshoot: SupportsFloat = 0.05,
max_num_spheres: SupportsInt = 3000,
surface_point_density: SupportsFloat = 30000.0,
surface_point_sampling_seed: SupportsInt = 123,
flip_normals: bool = False,
min_triangle_area: SupportsFloat = 1e-08,
) → list[cumotion.cumotion.CollisionSphereGenerator.Sphere]#

Generate a selection of collision spheres from a grid of points filling a triangle mesh.

NOTE: For most meshes, this generate_collision_spheres() function is expected to perform

better than CollisionSphereGenerator (which is likely to be deprecated).

The mesh is represented by triangles and vertices, where each triangle in triangles is a set of indices referencing points in vertices. At least three vertices and at least one triangle must be provided, and at least one triangle must remain after the culling described below.

The vertex indices of each triangle are valid if every index is in range [0, len(vertices)) and no index is repeated. Triangles with invalid vertex indices are culled prior to sphere generation and selection.

The max_overshoot serves as an upper bound for how far any collision sphere may extend beyond the surface of the mesh. The units of the max_overshoot are the same as the mesh, typically meters for robotics applications. The max_overshoot must be positive, and is clipped to the longest dimension of the axis-aligned bounding box enclosing the mesh.

Larger max_overshoot values will create conservative collision sphere representations with relatively few spheres (increasing performance for motion generation and collision checking). Smaller max_overshoot values will fit spheres more tightly to the mesh and will (in general) require more spheres to fit a given mesh (reducing performance for motion generation and collision checking).

The max_num_spheres sets an upper bound on the number of candidate spheres from which collision spheres will be selected. Specifically, the max_num_spheres is used to generate a grid of points filling the axis-aligned bounding box enclosing the mesh. These points serve as potential sphere centers. The max_num_spheres may need to be increased from the default value for particularly large meshes or for particularly small max_overshoot values. Increasing max_num_spheres will (in general) improve the selection of collision spheres, but result in slower generation time. The max_num_spheres must be positive, and is clipped to 256,000.

NOTE: The number of returned spheres will typically be orders of magnitude smaller than

max_num_spheres.

The goal of sphere selection is to select spheres such that the entire mesh surface is enclosed by one or more spheres. As an approximation, points are distributed uniformly on the mesh surface and used to test whether the surface is fully enclosed. The surface_point_density determines how many test points are distributed. The units for surface_point_density are 1 / [mesh-length-unit]^2. For the typical robotics case (with the mesh represented in meters), the default value corresponds to 3 surface points per cm^2. Using higher values for surface_point_density will increase the likelihood of full surface enclosure (at the cost of slower generation time). The surface_point_density must be positive. Changing the parameter surface_point_sampling_seed will result in different surface points being selected and cause different candidate spheres to be selected. This seed may be used, e.g., to randomly generate multiple sphere sets with the same max_overshoot.

The mesh input to generate_collision_spheres() is not required to be strictly watertight but is expected to generally represent a volume. In the current implementation, grid points are classified as interior or exterior to the mesh by counting ray crossings, which does not depend on the winding direction of the vertex indices. Thus, flip_normals has no effect on the returned spheres.

Very small and/or degenerate triangles are unlikely to aid in collision sphere generation. Thus, triangles with surface area less than or equal to min_triangle_area are culled prior to sphere generation and selection. The min_triangle_area must be positive.

A warning will be logged for each triangle in triangles with invalid vertex indices.

A warning will be logged, and parameter values will be clipped to their maximum if:

  1. The max_overshoot exceeds the longest dimension of the axis-aligned bounding box enclosing the mesh, OR

  2. The max_num_spheres exceeds 256,000.

A fatal error will be logged if:

  1. Fewer than three vertices or no triangles are provided,

  2. All triangles are culled due to invalid vertex indices or insufficient surface area,

  3. All vertices lie in a single plane perpendicular to the x, y, or z axis, OR

  4. The max_overshoot, max_num_spheres, surface_point_density or min_triangle_area parameters are not positive.
